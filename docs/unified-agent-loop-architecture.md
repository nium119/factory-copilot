# Factory Copilot 统一 Agent 循环架构设计

> 版本：v2（讨论收敛稿）
> 目标：把 FC 从「工具执行器」升级为「带护栏的任务自治体」，回应「不够智能、不像 DSH/Codex」的差距。

---

## 一、背景与目标

### 1.1 现状问题（病根诊断）

FC 当前「不够智能」的病根是**执行模型割裂**，而非缺 LLM 或缺框架：

1. **路径割裂**：单步（L2 路由）与多步（DynamicPlanner）是两条独立代码路径，靠启发式判断走哪条。
2. **确定性用错了层**：「触发词匹配 + 动词过滤」这种确定性规则被用于**意图理解**，导致「创建单据」这种模糊表达直接卡死报「无法操作」——理解本该是 LLM 的活。
3. **四源工具割裂**：本体动作、API、MCP、A2A 四类工具各自为政，LLM 规划时看不到完整能力。
4. **治理/权限/规则散落**：RBAC 在 action_executor、数据过滤在 apply_data_filters、审批门禁在 base.py、规则在 rule_engine，没有统一治理流水线。
5. **反馈不闭环**：执行失败就报错，缺少「反思 → 验证 → 回滚」的质量闭环。

### 1.2 目标

一个**带护栏的 DSH/Codex**：LLM 在理解层自由发挥（智能），确定性在执行层兜底（安全），Graph 在中间做确定性加速，Loop 把一切串成闭环。

---

## 二、设计原则（四条）

1. **理解归 LLM，执行归确定性**
   LLM 负责「想」（意图、规划、反问、异常判断、反思），确定性负责「做」（数据、权限、规则、审计、回滚）。护栏限制的是「做」，不是「想」。

2. **本体是能力边界**
   LLM 只能从本体（+ 四源工具注册表）里选动作，选不出就反问列能力，不允许幻觉出不存在的工具/字段。

3. **写操作永远过治理**
   确认 + RBAC + 数据权限 + 规则 + 审计 + 回滚，LLM 规划器无权绕过。

4. **Graph 是执行层的确定性加速器**
   图遍历（BOM 递归、影响扩散、关系链）是「执行」的确定性实现，不是「理解」的确定性路由；能图遍历就不让 LLM 逐步猜。

## 三、分层架构

```
┌──────────────────────────────────────────────────────────────┐
│ 入口层：对话 / SSE / A2A / 审批回传                            │
├──────────────────────────────────────────────────────────────┤
│ 观察层（统一拼装上下文）                                      │
│   消息 + 短期记忆 + 摘要记忆 + 长期记忆(向量)                  │
│   + 向量检索(skill/概念/文档) + 项目描述 + 领域知识(向量召回)   │
├──────────────────────────────────────────────────────────────┤
│ 理解层（LLM 主导，自由）                                      │
│   意图理解 · 语义匹配链 · 任务规划 · 反问澄清 · 异常降级      │
│   产出：「决定」= 动作+参数，或 ASK                            │
├──────────────────────────────────────────────────────────────┤
│ 执行层（确定性主导，护栏）                                    │
│   规划落地：单步路由 / 链执行 / Graph 图遍历                  │
│   治理流水线（六闸门）：                                      │
│     ① 工具边界 ② 操作权限RBAC ③ 数据权限(行/列)              │
│     ④ 业务规则constraint ⑤ 风险分级 ⑥ 审批门禁               │
│   四源工具：本体 + API + MCP + A2A                            │
│   执行后：trigger 预警 + inference 推理 + computed 计算        │
├──────────────────────────────────────────────────────────────┤
│ 反馈层（质量闭环）                                            │
│   反思(LLM) → 验证(确定性) → 失败则回滚(快照) → 成功则写记忆  │
│   不充分/失败 → 回到理解层继续循环                            │
└──────────────────────────────────────────────────────────────┘
        ↑____________________________________________|
                统一 Agent 循环（Loop）
```

**关键**：理解层（LLM）与执行层（确定性）之间是单向的「决定 → 执行」，执行结果经反馈层回流理解层，形成闭环。LLM 永远不直接碰数据和权限，确定性永远不猜用户意图。

## 四、核心组件

| 组件 | 职责 | 主导 | 现有代码映射 |
|---|---|---|---|
| **统一循环** | 观察→规划→执行→反馈 骨架 | Loop | 新写，收编 `base.py._standard_process` |
| **观察拼装器** | 消息+记忆+向量+项目描述+领域知识 统一成上下文 | 确定性 | 收编 message_service + vector_memory + RAG |
| **规划器** | 意图理解 + 任务规划 + 反问 + 异常判断 | LLM | 收编 L2 路由 + `_plan_steps` |
| **执行器** | 工具边界校验 + 六闸门治理 + 四源分发 | 确定性 | `action_executor` 保留增强 |
| **Graph 引擎** | 沿本体关系图确定性扩散 | 确定性 | 收编 `_recursive_pending`/BFS |
| **链执行器** | 用户预定义的多步路径 | 确定性 | 收编 `chain_engine` |
| **排程引擎** | 自适应 DP/遗传算法排程 | 确定性 | `scheduling_service`（已完成） |
| **治理流水线** | 六闸门统一拦截 | 确定性 | 收编 RBAC/DataFilter/rule_engine/审批 |
| **反馈器** | 反思+验证+回滚 | LLM+确定性 | 收编 reflect + verify_target + restore_entity |

## 五、数据流示例

### 例1「创建单据」——模糊意图（理解层主导）
```
观察层：消息「创建单据」+ 项目描述(APS) + 领域知识
理解层：LLM 理解"单据"模糊 → 本体检索出[工单/销售订单/采购订单] → ASK「你要创建哪种？」
用户选"工单" → 理解层决定 WorkOrder_create
执行层：边界校验 → RBAC → 数据权限 → 风险分级 → 审批确认 → 确定性创建
反馈层：验证创建结果 → 审计 → 写入记忆
```

### 例2「分析工单 WO-001 影响哪些物料」——Graph 场景
```
理解层：LLM 判断是"影响分析" → 决定调 Graph 扩散
执行层：Graph 引擎沿 BOM 递归关系确定性扩散（不 LLM 逐步猜）
反馈层：结果充分 → 汇总报告；不充分 → 反思补查
```

### 例3「创建工单并排程」——复合任务
```
理解层：LLM 规划 [WorkOrder_create → WorkOrder_schedule]
执行层：步1 确认+创建 → 步2 排程引擎(自适应DP/遗传算法)
反馈层：每步验证 → 失败则回滚 → 成功写记忆
```

## 六、与现状映射（改什么/保留什么/回退什么）

**保留**：
- `action_executor`（执行器，增强工具边界）
- 治理能力（RBAC/DataFilter/rule_engine/审批/审计）
- `scheduling_service`（自适应排程，已完成）
- Graph 能力（递归展开/BFS）
- 记忆 + 向量检索（vector_memory/vector_search）

**回退（前几轮方向错的"确定性理解"补丁）**：
- 第1步的「动词过滤」→ 回退为 LLM 理解 + 本体检索
- 第2步的「动作词计数」复合检测 → 回退为统一循环的 LLM 规划

**改造**：
- `base.py._standard_process` + `dynamic.py` → 统一成一个循环
- 新增「规划器」接口（LLM 观察→决定）
- 新增「工具注册表」（四源工具统一）
- 新增「治理流水线」（六闸门统一）

## 七、分阶段落地（增量，每步可验证）

| 阶段 | 内容 | 验证标准 |
|---|---|---|
| **A：工具注册表 + 循环骨架** | 四源工具统一注册；单步+多步收编成一个循环 | 现有对话不回归 |
| **B：理解层强化** | 规划器支持写操作+反问+异常降级；回退确定性补丁 | 「创建单据」「创建并排程」稳定 |
| **C：Graph-Loop 融合** | Graph 作为执行层确定性工具，LLM 可调用 | 「影响分析」既快又稳 |
| **D：治理流水线 + 反馈闭环** | 六闸门统一 + 反思/验证/回滚 | 写操作全链路可审计可回滚 |
| **E：任务级自治** | 长任务、跨 namespace、多 Agent 协作 | 复合指令自主完成 |

## 八、增强维度（生产化时补，非地基）

1. **可观测性**：每一轮循环留痕（tracing span 覆盖规划/执行/反馈，审计可追溯，span 能定位耗时大头）。
2. **模型/成本路由**：理解层用强模型（规划/反思），执行层零 LLM 成本（确定性），按复杂度动态选模型。
3. **多 Agent 协作 + LLM 安全护栏**：内部业务域 Agent 协同；prompt 注入防护 + 工具/字段名回落到本体防幻觉。

---

## 九、一句话总结

> **FC 统一 Agent = Loop 骨架 ×（观察层：消息+记忆+检索+项目描述+领域知识）×（理解层：LLM 自由规划）×（执行层：单步/链/Graph + 六闸门治理 + 四源工具）×（反馈层：反思/验证/回滚）。** 理解归 LLM（智能），执行归确定性（安全），Graph 做确定性加速，Loop 串成闭环。
